# Stage 5.4 — Controlled continuous Libretro rendering research

Status: Stages 5.4.1 through 5.4.4 are physically validated on the PW5.
Stage 5.4.2 performance instrumentation and the Stage 5.4.4 nearest-neighbor
optimization are implemented in the standalone live probe. It preserves the
single-threaded rendering policy and conservative 1 FPS default.

## Stage 5.4.1 implementation

`tools/libretro_live.c` is an isolated dynamically loaded frontend. It accepts
`CORE ROM [duration_seconds] [display_fps] [--warmup FRAMES] [--capture-only] [--scale MODE]`,
with defaults of 30 seconds, 1 display FPS, and 180 warmup runs. Warmup is
excluded from the measured interval. Video callbacks copy pitch-aware
XRGB8888 rows into owned memory and conversion uses the existing YA grayscale
formula. Emulation and display counters are kept separately and the newest
completed frame is retained; replaced frames are counted as skipped.

The build is isolated behind `host-libretro-live`, `docker-build-libretro-live`,
`libretro-live-host`, `libretro-live-kindle`, and `deploy-libretro-live`.
Host capture-only validation is:

```sh
make host-libretro-live
build/libretro_live-host build/sameboy/sameboy_libretro.so \
  third_party/sameboy/.github/actions/dmg-acid2.gb 5 1 --warmup 180 --capture-only
```

The successful host run confirms SameBoy loading, XRGB8888 negotiation,
continuous callbacks, warmup separation, bounded duration, and metrics output.
It does not exercise `/dev/fb0`, Kindle ABI compatibility, or physical refresh
latency. ARM artifact inspection and the physical commands remain:

```sh

make deploy-libretro-live
```

## Stage 5.4.3 — Scaling performance benchmark

The live probe supports three selectable modes through `--scale MODE`:

* `smooth` is the default and preserves the validated FBInk fit-to-viewport
  path (`scaled_width = scaled_height = -2`).
* `native` disables FBInk scaling and displays the original callback image
  centered on the viewport.
* `nearest` performs an aspect-preserving nearest-neighbor fit in C using a
  reusable YA destination buffer, then disables FBInk scaling. Its time is
  reported as `avg_nearest_scale_ms`; existing performance metrics remain.

Each display attempt logs `refresh_rect x=... y=... w=... h=...`. The first
flashing update is logged as the full viewport; later entries are the
rectangle returned by `fbink_get_last_rect(false)`. `WFM_AUTO`,
`fbink_wait_for_complete()`, framebuffer dump/restore, signal handling, and
the conservative 1 FPS default are unchanged. The initial 5.4.3 comparison
was measurement-only; the later 5.4.4 results are documented below.

For a same-ROM, ten-second, 1 FPS comparison with 180 warmup frames, run on
the PW5 from the deployed directory:

### Nearest-neighbor optimization research

The current implementation computes both source coordinates inside the pixel
loop. On ARMv7, these are 64-bit integer divisions repeated across the output
image. The horizontal division is repeated for every output pixel, and the
vertical division is repeated for every output row. The loop also recomputes
source and destination byte offsets and performs two YA-byte reads and two
YA-byte writes per output pixel. This is the leading likely cause of the
186.221 ms result; the benchmark does not yet prove how much is arithmetic
versus memory traffic or cache behavior.

For a typical PW5 fit of roughly 1.4 million output pixels, the destination is
roughly 2.6 MiB of YA data per frame for the documented 1236x1112 fit. The
current loop performs roughly 2.7 million source-coordinate divisions per
frame, plus index arithmetic,
while writing the same roughly 2.8 MiB. Exact output dimensions should be
taken from the device viewport and logged rectangles for each run.

The smallest safe optimization is to retain the current dimensions and
nearest-neighbor equations, but precompute reusable source indices once per
scaled frame:

- reuse scaled-width 32-bit horizontal indices and scaled-height 32-bit
  vertical indices;
- compute each index with the exact current integer formula;
- use row pointers and incrementing destination pointers in the pixel loop;
- copy the two YA bytes directly, avoiding repeated multiplications and
  divisions inside the inner loop.

This adds approximately (scaled_width + scaled_height) * 4 bytes (about
9.4 KiB for a 1236x1112 fit), while preserving the existing output byte for
byte. A row-pointer table is optional and unnecessary for the first change.
Repeated pixel-span reuse or integer replication is not recommended initially:
the fit is generally non-integral, and changing that behavior risks visible
differences. Compiler flags should be measured only as a secondary experiment;
the current -O2 build and FBInk flags are part of the existing contract.

### Pixel-identical validation strategy

Before any implementation change, capture the current nearest output for a
fixed synthetic YA frame and the same negotiated dimensions. Compare the
complete scaled YA buffer byte-for-byte against the optimized implementation,
including non-integral ratios, minimum dimensions, and the actual PW5
viewport. Also verify dimensions, allocation reuse, centering, refresh
rectangles, and avg_nearest_scale_ms. Host capture-only tests can validate
arithmetic and bounds; only the PW5 can validate timing and visual result.

## Stage 5.4.4 — Nearest-neighbor scaling optimization

The nearest scaler now precomputes horizontal and vertical source indices and
reuses those tables and the YA output buffer across frames. The inner loop
resolves one source row, advances the destination pointer by two bytes per
pixel, and copies YA pairs without repeating the previous per-pixel 64-bit
coordinate divisions or destination offset multiplication. The integer
mapping equations are unchanged.

The host-only `libretro-scale-test` compares the actual optimized scaler
against an independent reference implementation byte-for-byte across small,
non-integral, edge-case, and PW5-sized dimensions and multiple deterministic
pixel patterns. It also checks scaled dimensions and buffer reuse. This test
does not establish Kindle timing or visual performance.

Stage 5.4.4 does not change the smooth default, native mode, refresh policy,
WFM_AUTO, completion waits, screen restoration, or 1 FPS default. Physical
validation of the optimized ARMv7 binary is complete; the results below do not
claim that the full InkBoy application is playable.

### Stage 5.4.2 instrumentation implementation

The live probe now measures these independent intervals after warmup:

| Metric | Definition |
| --- | --- |
| `avg_emu_frame_ms` | Wall time spent inside each `retro_run()` call, averaged over measured runs; callback work invoked by the core is included. |
| `avg_callback_copy_ms` | Time to ensure/reuse producer storage and copy one pitch-aware XRGB8888 callback into owned memory. |
| `avg_convert_ms` | Time to ensure/reuse YA storage and convert one selected XRGB8888 frame. |
| `avg_fbink_draw_ms` | Time spent in `fbink_print_raw_data()`, including failed draw calls. |
| `avg_refresh_submit_ms` | Time spent in `fbink_refresh()` or `fbink_refresh_rect()` submission attempts. |
| `avg_refresh_wait_ms` | Time spent in `fbink_wait_for_complete()` for submitted refreshes. |
| `avg_schedule_ms` | Main-loop deadline/reporting decision time, excluding presentation and sleep. |
| `sleep_ms` | Actual elapsed time in `nanosleep()` calls used for emulation pacing. |

`emu_fps` is measured post-warmup runs divided by measured wall time.
`display_fps` counts only updates whose draw, refresh submission, and
completion wait all succeed. `scheduled_display_attempts` counts eligible
display deadlines with a completed frame, including failed attempts.
`refresh_attempts` counts calls to the explicit FBInk refresh API, while
`refresh_failures` includes draw, submission, region, and completion failures.
CPU percentage is process user-plus-system CPU time divided by measured wall
time; RSS is the process maximum resident set size reported by `getrusage`.

The producer and display XRGB buffers are now reused across callbacks and
display swaps when dimensions are stable. A reusable YA buffer removes the
per-update conversion allocation. Ownership remains explicit: the callback
only writes the producer buffer, and FBInk reads the selected display buffer
after the callback returns. This is an allocation optimization only; the
refresh policy, waveform selection, frame dropping, and single-threaded
ordering are unchanged.

The timers do not establish panel-side work or optical quality. Callback copy
timing includes storage growth when a frame size changes, refresh wait timing
includes kernel/driver/panel completion behavior, and scheduling timing is
too small to be meaningful when rounded to three decimals on some hosts.
No physical performance improvement is inferred from host capture-only runs.

## Stage 5.4.2 — Performance and refresh optimization research

This section is a research plan based on the validated 5.4.1 measurements. It
does not change the probe or claim that any optimization is safe on the PW5.

### Current bottlenecks and evidence

1. **Synchronous refresh reduces effective emulation throughput.** SameBoy
   reports a nominal 59.73 FPS, but each `retro_run()` averages 26.709 ms,
   already corresponding to about 37.4 calls per second before display work.
   The live loop calls `present_frame()` synchronously and waits for
   `fbink_wait_for_complete()` before continuing. Nine measured waits consume
   approximately 1.17 seconds in total (`9 × 129.812 ms`) during the 10-second
   run. This is the clearest cause of the measured 29.59 wall-clock emulation
   FPS.

2. **The new instrumentation can apportion the principal software stages.**
   It now measures video callback copy, XRGB8888-to-YA conversion,
   `fbink_print_raw_data()`, refresh submission, completion wait, scheduling,
   and sleep separately. New physical values are not available yet, so the
   Stage 5.4.1 values establish only:

   - `retro_run()`: 26.709 ms average;
   - refresh submission: 1.191 ms average, approximately 10.7 ms total;
   - refresh completion wait: 129.812 ms average;
   - conversion, FBInk drawing, callback copy/allocation, scheduling, and
     sleep: not measured in the Stage 5.4.1 log.

   The gap between the 26.709 ms `retro_run()` average and the approximately
   33.8 ms wall-clock cost implied by 29.59 FPS includes callback buffer work,
   conversion/drawing, refresh work, and scheduler overhead. It must not be
   assigned to grayscale conversion or FBInk drawing without new timers.

3. **Nominal pacing is not the main source of the 30 FPS result.** The loop
   schedules emulation from SameBoy's nominal timing, but resets the next
   emulation deadline when a run is late. Since a 26.709 ms run exceeds the
   nominal 16.74 ms period, the loop normally performs no catch-up burst and
   little or no emulation sleep. The display wait, not an intentional 60 FPS
   sleep, is the dominant known stall.

   The single-threaded architecture remains appropriate for the next
   measurement-only iteration because it preserves strict refresh ordering and
   simple restoration. It is not appropriate if the goal becomes maximizing
   emulation throughput while a refresh is pending; that requires a separate
   producer/display design and new synchronization risks.

4. **Frame ownership work is more frequent than presentation.** The video
   callback still copies a complete XRGB8888 frame for every valid callback,
   but Stage 5.4.2 reuses the producer/display allocations when dimensions are
   stable. The 294 skipped-frame count confirms that most captured frames are
   replaced before a display deadline. A valid callback still has to be copied
   unless the core's buffer lifetime is explicitly guaranteed.

5. **Partial regions are FBInk-drawn regions, not image-difference regions.**
   After each raw draw, the probe asks `fbink_get_last_rect(false)` for the
   rectangle FBInk most recently drew and submits that rectangle with
   `fbink_refresh_rect()`. This is the correct API sequence for the current
   scaled game rectangle, but it does not compare old and new frames. The
   entire scaled game rectangle is written to the framebuffer on each update,
    and the returned rectangle coordinates and dimensions are logged for each
    display attempt.

### Capture-only versus live benchmarks

Capture-only and live runs are comparable for post-warmup callback/copy and
`retro_run()` measurements when they use the same ROM, warmup, duration, and
binary. Capture-only omits FBInk initialization, YA conversion, drawing,
refresh submission, and completion waits, so its wall-clock emulation rate is
an upper-bound baseline rather than a display-rate target. Compare both
`avg_emu_frame_ms` and wall-clock `emu_fps`; do not compare capture-only FPS
directly with display FPS.

### Ghosting and visual-quality measurement

Future tests should keep the configured display rate at 1 FPS or lower until
the panel behavior is characterized. Use repeatable scenes and record the
same measured fields plus refresh completion time. For each run, separately
record readable detail, flash behavior, residual image after scene changes,
and grayscale fidelity. A fixed test sequence can alternate dark/light blocks,
static game scenes, and a cleanup full refresh. An external camera or other
repeatable optical observation is needed for objective panel ghosting; an
FBInk framebuffer dump only describes memory, not the panel's optical state.

### Recommended incremental improvements

| Priority | Change | Expected benefit | Complexity/risk |
| --- | --- | --- | --- |
| 1 | Repeat the instrumented 1 FPS physical run and log returned region dimensions | Separates the remaining software overhead and verifies region behavior on the PW5 | Low; measurement only |
| 2 | Compare allocation/reuse timing and RSS across identical host capture-only runs | Quantifies the safe allocation optimization without changing refresh behavior | Low; host-only evidence |
| 3 | Add unchanged-frame detection and avoid a draw/refresh when the latest image is identical | Can remove redundant writes in static scenes | Low/medium; requires a checksum or comparison and must not hide needed cleanup refreshes |
| 4 | Measure a bounded matrix of full versus partial updates at the existing 1 FPS rate, including a periodic full cleanup | Establishes ghosting/latency tradeoffs without assuming an ideal FPS | Medium; physical observation required |
| 5 | Prototype a producer/display split with explicit ownership and a latest-frame queue | Prevents refresh waits from stopping emulation; likely improves emulation throughput | Medium/high; synchronization, shutdown, and FBInk ordering risk |

The recommended next experiment is Priority 1: repeat the same 10-second
Pokémon Yellow test at 1 FPS with the instrumented Kindle binary and record
the new per-stage timings and returned partial-refresh rectangle. This
preserves the validated rendering behavior while identifying whether the next
optimization target should be callback copying, conversion, FBInk drawing, or
the synchronous wait. Only after that baseline should a two-thread
producer/display prototype be considered.

### Remaining uncertainties

- The current data does not isolate grayscale conversion, FBInk drawing, or
  callback allocation time.
- It is not known whether the 129.812 ms completion wait is panel-limited,
  kernel scheduling, or a FBInk/firmware interaction.
- The actual dimensions returned by `fbink_get_last_rect(false)` have not been
  recorded on the PW5.
- The best partial/full-refresh policy and any ghosting cleanup interval are
  unknown.
- A two-thread design may improve emulation throughput but could alter update
  ordering or restoration safety.

## Objective and constraints

The next experiment should run SameBoy for a bounded or explicitly terminated
session while displaying selected frames through the existing vendored FBInk
API. Emulation cadence and display updates must be separate decisions. The
device's sustainable display rate is unknown and must be measured on the
physical PW5 running firmware 5.19.2; this document does not assume a target
FPS.

The implemented probe is single-threaded and conservative: it runs one
`retro_run()` at the core's nominal cadence, copies valid callbacks into owned
memory, and submits at most one display update per monotonic display deadline.
FBInk is initialized and dumped before the measured loop. The newest completed
frame is converted and drawn in the loop; each refresh is submitted and waited
for before another one is attempted. The default display rate remains 1 FPS.

## 1. Libretro video callback lifecycle

The frontend registers `retro_video_refresh_t` with
`retro_set_video_refresh()` before the first `retro_run()`. The core invokes
that callback from inside `retro_run()` when it has video output. One
`retro_run()` normally represents one emulated frame, but the frontend is
responsible for pacing calls and the callback count is not a guaranteed
one-to-one mapping:

- a core may produce zero, one, or more callbacks during a run;
- `data == NULL` requests duplication of the previous frame when duplication
  is supported;
- `width`, `height`, and `pitch` belong to that callback and must be honored;
- the callback's source pointer must not be retained after the callback or
  assumed to remain valid across later `retro_run()` calls.

SameBoy currently negotiates XRGB8888. The existing probe must continue to
accept only the confirmed format and must keep reporting measured
`retro_run()` and video-callback counters. A continuous frontend should also
record submitted display updates, skipped display opportunities, and refresh
completion times.

The core's `retro_get_system_av_info()` supplies nominal geometry and timing,
including the expected emulation FPS. That value is useful for emulation
pacing and diagnostics, but it is not evidence that the PW5 can refresh at the
same rate.

## 2. Frame buffering and ownership

The Stage 5.3 probe already copies each valid callback row by row into a
tightly packed owned XRGB8888 buffer. That ownership rule should remain the
boundary between SameBoy and the display path.

For the first continuous experiment, use two small owned frame buffers:

1. the callback writes the newest complete frame into the producer buffer;
2. after `retro_run()` returns, the main loop swaps or copies it into the
   display buffer if a display deadline is due;
3. FBInk reads only the stable display buffer until the raw-data call returns.

With one thread, this can use an ordinary buffer swap because the callback and
FBInk submission are serialized. If a future design adds an emulation thread,
use a mutex or a carefully documented atomic sequence/index protocol; do not
read a buffer while the callback is writing it. Avoid allocating memory or
calling FBInk from the video callback.

Retain only the newest complete frame. Queuing every frame increases memory,
latency, and E-Ink work without improving the visible result. A frame checksum
or a small metadata comparison can skip a display update when the image is
unchanged.

## 3. XRGB8888 to grayscale

The current conversion remains appropriate:

```c
uint8_t y = (uint8_t)((77U * r + 150U * g + 29U * b + 128U) >> 8);
```

Extract `R`, `G`, and `B` from the XRGB8888 word without assuming an unaligned
pointer. Convert outside the callback when possible, then store packed YA
(`Y`, opaque `0xff`) for `fbink_print_raw_data()`. The row pitch is used only
while copying the source; the retained and converted buffers are tightly
packed.

At `160x144`, the XRGB source is 92,160 bytes and the YA frame is 46,080
bytes. This is small enough for two buffers on the PW5. The full-screen FBInk
working buffer remains substantially larger, so memory measurements should
include the process RSS during repeated updates.

## 4. E-Ink scheduling and synchronization

E-Ink refresh is asynchronous from the caller's perspective. A successful
`fbink_refresh()` means the update was accepted, not necessarily that the
panel has finished changing. The existing sequence should be preserved:

1. write raw YA data with `no_refresh = true`;
2. request one explicit refresh;
3. call `fbink_wait_for_complete(fbfd, LAST_MARKER)`;
4. only then submit the next update or restore the saved screen.

Use `clock_gettime(CLOCK_MONOTONIC, ...)` for the display deadline. The first
prototype should expose the display interval as a command-line or experiment
parameter and log the actual interval and wait duration. Do not derive a
fixed display FPS from the nominal SameBoy FPS, the 60-frame Stage 5.2 test,
or one successful boot-logo refresh.

The safest initial scheduling policy is:

- call `retro_run()` at the chosen emulation cadence;
- when the display deadline is reached, present the newest complete frame;
- wait for FBInk completion before another present;
- count skipped frames while a refresh is pending or while the deadline has
  not arrived.

Once latency is measured, emulation can continue between display updates and
the frontend can intentionally drop intermediate frames. The display path
must never attempt to catch up by issuing a burst of queued refreshes.

## 5. Partial and full refresh

The first live update uses the verified Stage 5.3 path: `is_cleared = true`,
YA raw drawing with `no_refresh = true`, and an explicit full-screen refresh
with `is_flashing = true`. Later updates do not clear the screen, use
`fbink_get_last_rect(false)`, and request a non-flashing region refresh with
`wfm_mode = WFM_AUTO`.

FBInk's normal non-flashing path requests a partial update. A future experiment
can compare:

- partial updates for small, sparse changes;
- periodic full updates to clear accumulated ghosting;
- full updates after scene changes or before restoration.

The update region should be limited to the actual scaled game rectangle when
that is safe, but the first comparison should preserve the existing centered
`-2/-2` scaling and explicit refresh sequence. Region behavior, clearing, and
the interaction between `is_cleared`, `no_refresh`, and scaling must be
verified on hardware rather than inferred from host behavior.

## 6. Waveforms and ghosting

`FBInkConfig.wfm_mode` should remain `WFM_AUTO` until the PW5 results are
measured. The device reports an MTK PW5 with Eclipse waveform support, but
that capability does not establish that every waveform is suitable for this
application or for the vendored FBInk revision.

For each candidate mode, record:

- refresh completion time;
- whether the image is readable;
- visible flash and ghosting after repeated updates;
- grayscale fidelity for dark and light regions;
- behavior after a full cleanup refresh.

Fast or monochrome waveforms may reduce latency while increasing ghosting or
discarding grayscale detail. A practical policy is likely to use a conservative
mode for normal updates and a periodic full/high-quality cleanup, but the
period and waveform must remain measured parameters. No fixed update count or
FPS should be committed before physical testing.

## 7. Frame skipping and independent display updates

Emulation frames and visible updates should have separate counters:

```text
retro_runs
video_callbacks
valid_frames
display_updates
skipped_display_frames
refresh_waits
```

The frontend presents the newest valid frame at most once per display deadline.
`display_updates` increments only after successful submission and completion;
refresh submission and wait failures increment `refresh_failures` and stop the
loop. Timing metrics measure `retro_run()`, refresh submission, and completion
waits separately. CPU percentage uses the process user/system CPU delta over
the measured wall interval; RSS uses `getrusage`.

The implementation uses a configurable interval and finite duration for
reproducible tests. Capture-only mode retains nominal emulation pacing while
omitting FBInk.

## 8. Shutdown and restoration

Save one framebuffer dump before the first display update. A signal handler
should only set a `sig_atomic_t` stop flag. At the next safe point:

1. stop calling `retro_run()`;
2. wait for any submitted FBInk refresh to complete;
3. unload the ROM and deinitialize SameBoy;
4. restore the saved framebuffer;
5. wait for restoration completion;
6. free the dump and buffers and close FBInk/core resources.

If an error occurs after `fbink_dump()`, attempt the same restoration path and
report both the original and restoration errors. SIGKILL, power loss, and a
process crash cannot guarantee restoration. A finite diagnostic mode should
remain available so tests do not depend on signal delivery or an interactive
shell.

## 9. Relationship to the existing interface and controls

Stage 5.4 should initially remain a standalone `tools/` experiment. It should
not add a second touchscreen reader or call the existing virtual-control code
from inside SameBoy. The future input adapter should map the existing control
state to Libretro's `retro_input_state_t` IDs, while `retro_input_poll()` only
marks the point at which the current state is sampled.

The existing `src/main.c` framebuffer ownership, virtual control layout, and
screen restoration behavior must remain unchanged until continuous rendering
has passed a separate hardware test. If integration is later approved, the
emulation/display scheduler should be introduced behind the existing
application lifecycle rather than duplicating FBInk initialization or dump/
restore ownership.

## Recommended incremental implementation plan

1. Add instrumentation only: nominal core timing, callback counters, frame
   checksum, display-update counters, and refresh duration.
2. Add a single-threaded latest-frame buffer and configurable display
   interval, with no touchscreen integration and a finite run limit.
3. Measure the PW5 using the existing full-refresh path at several intervals;
   record completion latency, CPU, RSS, skipped frames, and visible artifacts.
4. Compare partial versus full refresh and a small set of device-supported
   waveform choices. Add periodic full cleanup only after the comparison.
5. Add the existing virtual-control state as a Libretro input adapter while
   preserving the current `src/main.c` behavior.
6. Consider integration only after the standalone experiment has a documented
   shutdown, restoration, and hardware result.

## Known risks and open questions

- The PW5's sustainable update rate and refresh latency are not measured.
- Partial updates may ghost heavily or behave differently for a large scaled
  rectangle than for a small region.
- The vendored FBInk revision and Kindle firmware may constrain waveform and
  update-region combinations.
- Continuing emulation while an E-Ink refresh is pending may increase CPU use
  without improving the visible result; this must be measured.
- A changed frame can still be visually indistinguishable after grayscale
  conversion, so checksum-based presentation decisions need a visual check.
- Restoring the prior screen while an update is pending can race the panel if
  completion is not awaited.
- The current Stage 5.3 boot-logo result validates one frame and restoration,
  not gameplay responsiveness, control latency, or continuous rendering.

No new dependency is required. The existing Libretro headers, SameBoy core,
vendored FBInk API, Kindle toolchain, and Docker workflow are sufficient for
the next research implementation.
